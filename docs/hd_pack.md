# HD Pack как addon — осуществимость, архитектура, бюджет

> Вопрос: можно ли переработать графику и оформить это как addon (не трогая
> `original/` и не ломая пиксельные baseline-тесты)?
>
> Ответ: **да, механизм addon'а реализуем малой кровью, а сам «HD» распадается на
> 4 независимых уровня**, у которых разная цена. Ниже — замеры по реальным данным и
> точки инъекции в код. Ничего в движке пока не менялось: это план.

Замеры сделаны на `original/` (GOG-релиз) инструментами репозитория
(`tools/res_msk.py`, `tools/b3d_full.py`) и прогоном `build/ht2re`.

---

## 0. Почему это реально (три готовых задела)

1. **Данные читаются в рантайме, конвертаций нет** (`PLAN.md`, «Принцип»). Значит
   оверрайд ассета — это вопрос приоритета в загрузчике, а не переупаковки игры.
2. **Оригинал сам хранит текстуры цепочкой LOD**: `<tile>.res` / `<tile>1.res` /
   `<tile>2.res`, и движок уже разрешает её правилом «первый файл побеждает
   (высшая деталь)» (`src/world/SceneTextures.cpp:103-118`). Проверено численно:
   `aa` 3.28 → 1.07 → 0.39 MB RGBA, `ad` `grass1` 256² → 128² → 64². То есть
   «HD-набор» — это буквально ещё один, более высокий уровень той же цепочки.
3. **Прецедент неразрушающего слоя уже есть**: `src/world/Overlay.{h,cpp}` +
   `--overlay FILE` (`docs/editor.md`) — правки редактора живут в отдельном файле,
   один парсер на два бинарника, `original/` не меняется. Addon — та же идея,
   только для ассетов.

Дополнительно: `B3D` хранит позиции как **float32 без квантизации**
(`B3D.h:52`, `B3D.cpp:266-267`), ничего не индексируется позиционно (якоря/линки/
ноды — `map<string,…>`), потребление байт 100.00% на всех 45 файлах. Значит
геометрию тоже можно подменить данными, а не кодом.

## 1. Четыре уровня «HD» и что каждый стоит

| Уровень | Что даёт | Нужен addon? | Правки кода |
|---|---|---|---|
| **0. Дешёвые победы** | MSAA, sRGB/гамма, поднятый LOD-bias, кривая тумана, пост-грейд одним проходом, дальность, инстансинг парковок | нет | только рендерер/App |
| **1. HD-текстуры** | Вся альбедо-графика в 2–4× (дороги, трава, дома, машины, UI) | да | VFS + ключ + PNG/DDS |
| **2. HD-геометрия** | Более плотные тайлы ENV, пропсы, машины; LOD/стриминг | да (тот же VFS) | почти нет, но нужен валидатор |
| **3. Материалы/шейдеры** | Нормал-мапы, specular/emissive, полупрозрачность, тени, HDR/тонмаппинг | нет (это движок) | 1–3 недели, высокий риск |

Уровни 1 и 2 укладываются в понятие «HD Pack как addon». Уровень 3 — уже
ремастер движка, addon'ом он не становится.

Экстраполяция только по **используемому** набору ENV (296 текстур):

| Вариант | GL-память |
|---|---|
| как сейчас (1×) | 29 MB |
| 2× (в 4 раза текселей), RGBA8 | 117 MB |
| 4×, RGBA8 | 468 MB |
| 4×, BC1/BC3 (сжатые) | **58 MB** |

Вывод: **4× HD без сжатия — это +468 MB только на мир**, плюс текущие утечки.
Поэтому сжатые форматы (DDS/BC7 или KTX2) — не «потом», а часть фундамента
уровня 1. Масштаб плотности: дороги ~13 текселей/юнит (7.6 см/тексель),
`grass1` ~11.5 текселей/юнит — 4× даёт ~2–3 см/тексель, дальше смысла мало,
упор в мипы и анизотропию (сейчас cap 8:1, `Renderer.cpp:123`).

## 3. Архитектура addon'а

### 3.1 Слой ассетов (VFS)

Сейчас все пути собираются как `opt_.dataDir + "/…"` — **135 мест** в `src/`
(+`tools/editor/`). Предлагается один класс `Assets`:

```
Assets::path("ENV/aa.b3d")   // пак(и) в порядке приоритета, затем dataDir
```

`--addon DIR` (повторяемый) + автоскан `addons/*/pack.json`. Порядок загрузки
детерминирован (id + priority), конфликты логируются. Пустой пак не меняет
ни одного пикселя — это A0-критерий.

### 3.2 Манифест пака

```json
{ "id": "hd-tex-2x", "name": "HT2 HD Textures", "version": "1.0",
  "priority": 10, "requires": ["ht2re>=0.9"],
  "scale": 2, "format": "auto",
  "containers": ["ENV/*", "COMMON/TRUCKS", "COMMON/CABINES", "MENV/dr"],
  "textures": { "key": "container-qualified" } }
```

Раскладка файлов — **контейнерно-квалифицированная**, иначе не адресуемо:

```
<pack>/ENV_aa/txr/road2.png        # тайл aa, текстура txr\road2.txr
<pack>/COMMON_TRUCKS/txr/truck01.png
<pack>/MENV_dr/txr/grass2.png
<pack>/UI_LOAD/m/singl_a.png
```

### 3.3 Точки инъекции (по убыванию отдачи)

1. **`SceneTextures::load`** (`src/world/SceneTextures.cpp:100-119`) — между
   `normalize()` (:116) и `Texture::decode` (:119). Покрывает ENV×39, COMMON,
   TRUCKS, CABINES, MENV, HUD-полосу. **Единственное место, где можно починить
   коллизию ключей** (см. §4.1).
2. **`Res::load`** (`src/res/Res.cpp:29`) — пост-парс merge: одним движением
   покрывает все `Res::find`-потребители (меню, ESC, загрузка, карта, HUD-маски).
3. **`Mask::decode` / `Texture::decode`** (`src/res/Mask.cpp:56,117`) — добавить
   имя/хук: перехватывает все 11 мест декодирования, позволяет PNG/DDS обойти
   палитру, RLE и colour-key.
4. **`Renderer::createTexture`** (`src/gfx/Renderer.cpp:1402`) — низкий рычаг:
   имя тут недоступно, но здесь живут мип-цепочка, анизотропия и будущий
   `glCompressedTexImage2D`.

### 3.4 Форматы

* **PNG RGBA8** — минимум (нужна настоящая альфа, см. §4.2). Vendored `stb_image`
  без новой системной зависимости (сейчас в проекте нет ни `SDL_image`, ни `stb`).
* **DDS (BC1/BC3/BC7) или KTX2** — обязательны для 4×; в `GLCore.h` нет
  `glCompressedTexImage2D`, его надо добавить.
* non-POT — уже законно в GL 3.3 core (940 из шипнутых текстур не-степени-двойки).
* UI-арт: **точные размеры**, иначе лейаут поедет (HUD 1600×50 1:1,
  `Hud.cpp:30-40`; `esc16` 1600×1200/215/225/640, `EscMenu.cpp:210,298,355`;
  меню 125×125, `Menu.cpp:150-155`).

### 3.5 CLI

`--addon DIR` (повторяемый), `HT2_ADDONS` (env), `--pack-info` (диагностика:
сколько ключей перекрыто, сколько не найдено, бюджет VRAM). По умолчанию пак
**выключен** — пиксельные baseline'ы `tools/shot_test.py` остаются зелёными.

## 4. Ловушки и блокеры (все проверены на данных)

### 4.1 ❗Ключ текстуры не содержит контейнер — 18.7% текстур мира сейчас «чужие»

`normalize()` (`SceneTextures.cpp:11-20`) отбрасывает каталог, а `map_` живёт
между вызовами `load()`. 6 711 записей ENV сворачиваются в **603 ключа**, и для
242 имён материалов, общих для нескольких тайлов (`mat_road2` — в 27 тайлах,
`mat_refl_road` — в 36), побеждает первый по алфавиту тайл, который это имя
содержит. Замер: из 1 351 пары «(тайл, текстура), запрошенных материалами»,
**253 (18.7%) получают пиксели другого тайла**. То же в CABINES (3×347→347) и
TRUCKS (4×702→702).

Следствия: (а) это существующий баг верности оригиналу; (б) пока он не исправлен,
per-tile HD-текстуры физически неадресуемы. Квалификация ключа по `resBase` —
обязательная часть уровня 1, а не «улучшение потом». Для пака это разница между
**296** глобальными ключами и **1 196** парами (тайл, имя).

### 4.2 Colour-key: у `.txr` нет альфы

Прозрачность задаётся ключом `RGB565(PALT[col-1])` из таблицы `MATERIALS`
(`ttx N`, `col C`) — `SceneTextures.cpp:59-98`, `Mask.cpp:143-165`. Всего
4 ключевых цвета. Наивный «апскейл `.txr` в PNG» **ломает вырезы**: бинарный
порог `texel.a < 0.5 discard` (`Renderer.cpp:170`) на ресемпленном арте даёт
чёрную кайму/дыры. Правильно: в HD-паке для keyed-материалов отдавать настоящую
альфу (`alpha=0` там, где был ключ) — шейдер уже умеет `discard`, правок не надо.
Дополнительно: `ttx N` — **порядковый** номер записи в `.res`, так что
переупаковка контейнера молча сдвигает все ключи; манифест пака должен
фиксировать пару (контейнер, запись), а не номер.

### 4.3 8bpp-палитра

172 текстуры `LOAD.RES` (front-end, per-texture BGR-палитра, index0 = ключ) и
186 масок 8bpp с встроенной палитрой 768 байт. Для них нужен либо новый путь
декодирования (PNG/DDS минует палитру), либо ре-энкод.

### 4.4 Утечки и лишние загрузки — HD их умножит

* `SceneTextures` **не имеет деструктора** и никогда не зовёт `Renderer::deleteTexture`
  (единственные вызовы — `Video.cpp:167,299`, `Mirror.cpp:210`). `Hud::load` держит
  `tablo_` от **локального** `SceneTextures` (`Hud.cpp:67-80`) — то есть утечка
  сейчас случайно работает как владение; при добавлении деструктора нужен
  владелец/refcount, иначе HUD потеряет текстуру.
* `skipNoLoad=true` применяется только к `COMMON` (`App.cpp:127,2798`). Поэтому
  `TRUCKS.RES` грузит все 702 текстуры, хотя 634 помечены `noload` (67 MB вместо
  ~8), а `CABINES.RES` — все 347 (340 `noload`). Оригинал эти текстуры
  догружает по требованию; нам нужен тот же отложенный путь.
* `vehicleTex_`/`worldTex_` загружают `TRUCKS.RES` дважды в разных сценариях —
  при HD это двойной бюджет.
* `SceneTextures::textureFor` имеет fallback по 4-символьному префиксу, который
  обходит `unordered_map` (`SceneTextures.cpp:162-165`) — при добавлении ключей
  маршрутизация становится недетерминированной. Пак должен это отключать/логировать.

### 4.5 Геометрия: что нельзя потерять

Подмена `.b3d` данными **не требует правок кода** (VFS отдаёт файл из пака), но
пак обязан сохранить: локальный origin/pivot (якоря задают мировой трансформ;
`lep12` — пример модели вне центра, `docs/b3d_transform.md:390-395`), имена
контейнеров/якорей/линков, имена материалов, имена group-нод `subtag 21`
(1 365 key-нод в ENV; скрипты/гейты ими рулят), один из известных vertex-форматов,
правило «первый dword полезной нагрузки = индекс вершины».

Связанные с геометрией подсистемы, которые пак молча сдвинет:
`Collision::build` (материал + наклон ≤37°), `GroundMap` (потолок тайла 12 юнитов,
299 224 треугольника → 80 827 клеток), `RoadSurface` (17 road-материалов +
горизонтальность), `modelGroundOffset()` (низ модели) и `modelBody()` (bbox →
капсула ИИ). Практический вывод: в манифесте нужен флаг `geometryAffectsGameplay`,
иначе пак может «поехать» по коллизии.

### 4.6 Чего пак не сможет без правок движка

* **Нормал-мапы**: в vertex-формате есть нормаль, но **нет тангенса**, а UV-сет
  ровно один (второй/третий есть только в fmt `0x102/0x202/0x203` и не читается,
  `B3D.cpp:674-677`). Авторские нормали игнорируются — считаются сглаженные
  (`B3D.cpp:529-563`).
* **Второй UV-сет / lightmap**: в данных `coord N` встречается только на воде и
  отражениях (264 строки `mat_bump_*`/`mat_refl_*`) — лайтмапов нет вообще.
* **Рельеф**: `MTR/terrain{0,1,2}.raw` жёстко проверяется как ровно 257²×2 байта с
  равенством байт в паре (`Terrain.cpp:15,26`) — заменить/уплотнить рельеф данными
  нельзя, только кодом. Рисуемая земля — билинейная выборка 8-битной карты, так
  что тесселяция рельефа ничего не добавит.
* **Полупрозрачность**: 3D-альфа только бинарный cutout, `GL_BLEND` для 3D выключен
  (`Renderer.cpp:170,1286`) — стекло/вода/фары требуют нового прохода.
* **Цвет**: нет sRGB, нет тонмаппинга, нет пост-обработки; render target'ы есть
  (зеркало, `Renderer.h:221-240`) и переиспользуемы под один пост-проход, но
  глубина там renderbuffer, а не текстура.
* **UI**: нет 9-slice/вектора/DPI; лейаут — литеральные пиксельные константы на
  двух разрешениях авторинга.

### 4.7 Риск тихой ошибки в парсере B3D

Загрузчик **не строгий**: неизвестный subtag/хвост/формат пропускается, а
`consumed()/total()` только логируется (`B3D.cpp:445-450`); при неудаче тайл
молча выпадает (`App.cpp:1789`). Значит для пака обязателен валидатор, который
проверяет `consumed == 100%`, сохранность имён материалов/групп и pivot'ов.

### 4.8 Тесты и лицензия

`tools/shot_test.py` — пиксельные проверки состояний. Любой addon **выключен по
умолчанию**, иначе baseline'ы краснеют. Нужен отдельный набор: (а) «пак не
включён → кадр идентичен», (б) «пак включён → покрытие/декод/структурные
проверки», а не побайтовое сравнение с оригиналом.
Лицензионно: апскейл оригинальных `.txr` — производная работа; пак должен
содержать авторский арт (или только инструменты генерации), а не пережатые
оригинальные битмапы.

один грейд-проход через существующий RenderTarget; трава вместо плоского тинта
земли (`Renderer.cpp:656` + уже готовая подстановка `App.cpp:675-681`);
инстансинг парковок.

## 6. Что нужно решить до старта

1. **Объём**: только HD-текстуры (A0–A3) или ещё геометрия (A4) и ремастер-шейдеры (A5)?
2. **Кто рисует арт**: пак — сторонний арт (делаем механизм + тулчейн + валидатор)
   или мы сами генерим (апскейл/перерисовка) — от этого зависит и лицензия, и
   требования к формату.
